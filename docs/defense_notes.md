# Как работает система: разбор для защиты

Файл для подготовки к защите практик 1–3. Не входит в отчёт.

---

## 1. Что система делает одной фразой

Каждые сутки по UTC система забирает данные с биржи OKX и от Банка России,
проверяет их, складывает в витрину и на её основе будет прогнозировать два
показателя следующего дня: объём торгов BTC/USDT и волатильность.

Сейчас работают три этапа из пяти: **загрузка → очистка → витрина**.
Модели и дашборд — впереди.

---

## 2. Путь одной записи через систему

Проследим, что происходит с данными за 18 сентября 2026 года.

### Шаг 1: OKX отдаёт массив чисел

```
["1758153600000","115234.1","116890.0","114002.5","116103.2",
 "8849.36030363","1027384512.4","1027384512.4","1"]
```

Девять элементов: время начала суток в миллисекундах, четыре цены
(открытие, максимум, минимум, закрытие), объём в BTC, два оборота и признак
завершённости.

**Важно:** последний элемент `"1"` означает, что сутки закрыты. Пока идут
текущие сутки, там `"0"`, и такая свеча **не сохраняется** — иначе в данных
оказался бы неполный день.

### Шаг 2: строка попадает в слой `raw`

```sql
raw.okx_btc_usdt_daily
  candle_date   = 2026-09-18
  high          = 116890.0
  low           = 114002.5
  volume_btc    = 8849.36030363
  source_json   = ["1758153600000","115234.1", ...]   ← исходник целиком
```

Рядом с разобранными полями лежит **исходный JSON**. Это нужно для
прослеживаемости: если значение на дашборде вызовет сомнение, можно дойти до
байтов, которые прислала биржа.

### Шаг 3: слой `clean` проверяет строку

Семь проверок. Например: максимум не меньше минимума, цены открытия и
закрытия лежат внутри диапазона, объём не отрицательный. Строка прошла — она
в `clean`, а в журнал `data_quality_log` попадает запись «проверки пройдены».

### Шаг 4: слой `mart` строит строку витрины

```
candle_date       = 2026-09-18      ← сутки, о которых строка
volume_btc        = 8849.36         ← что было в этот день
volatility_pk     = 0.0389          ← посчитано из high и low
volume_lag_1      = 5005.71         ← объём за 17 сентября
volume_mean_7     = 5522.47         ← среднее за 7 предыдущих дней
usd_rub           = 84.5093         ← курс ЦБ
usd_rub_age_days  = 0               ← курс свежий, того же дня
target_volume_btc = 4232.76         ← объём за 19 сентября ← ЦЕЛЬ
```

Всё выше `target_` — **признаки**, известные вечером 18-го.
`target_` — **ответ**, который модель должна научиться угадывать.

## 3. Четыре требования методички и как они выполнены

Это самая вероятная тема вопросов по практике 2.

### Инкрементальность
Загрузчик спрашивает базу: «какая последняя дата уже есть?» — и запрашивает
с **следующего** дня. Код:

```python
prior = conn.execute(select(func.max(date_column))).scalar_one()
start = prior + timedelta(days=1) if prior else first
```

Первый запуск качает с 2018 года, второй — только новые сутки.

### Идемпотентность
«Повторный запуск даёт тот же результат». Достигается по-разному на двух
этапах:

- **Загрузка**: вставка `ON CONFLICT DO NOTHING`. Уникальный ключ —
  инструмент + дата. Повторная строка просто не вставится.
- **Слои clean и mart**: перестраиваются **целиком** внутри одной транзакции
  (`DELETE`, затем `INSERT`). Сколько раз ни запусти — состояние одинаковое.

**Доказательство:** второй запуск показал `rows_added: 0`.

### Устойчивость к сбоям
Три уровня:
1. Временные ошибки сети (429, 500, 502, 503, 504) повторяются
   автоматически — до 3 раз с нарастающей паузой.
2. Вся загрузка идёт **в одной транзакции**. Обрыв на середине →
   откат целиком. Частично записанных данных не бывает.
3. Ошибка записывается в `load_log` со статусом `failed` и текстом.

### Журнал загрузок
Таблица `load_log`: номер, источник, время, статус, получено строк,
добавлено строк, последняя дата, текст ошибки.

## 4. Главная идея практики 3: защита от утечки будущего

**Если на защите спросят один вопрос — скорее всего этот.**

### Что такое утечка
Модель при обучении случайно видит данные, которых в реальности в момент
прогноза не будет. Результат: на проверке точность отличная, в работе —
провал.

Пример: если в признаки дня 18 сентября попадёт объём за 19-е, модель просто
«спишет ответ».

### Три меры в коде

**1. Цели отделены от признаков.**
`target_volume_btc` и `target_volatility_pk` лежат в отдельных полях, берутся
из дня `d+1` и никогда не используются как входные данные.

**2. Окна не включают текущий день.**
```python
start = max(0, i - window)
values[f"volume_mean_{window}"] = _mean(volumes[start:i])
                                                    # ↑ i, а не i+1
```
Срез `[start:i]` заканчивается **до** текущего дня. Если бы писали `[start:i+1]`,
среднее косвенно содержало бы сегодняшнее значение.

**3. Курс ЦБ ищется только назад.**
```python
for rate_date, value in rates:
    if rate_date <= day:      # ← только не позже текущего дня
        chosen = (rate_date, value)
    else:
        break
```

### Как это доказано
Тест `test_no_target_leaks_into_features`: кладёт в следующий день заведомо
отличающееся значение 999 и проверяет, что оно **не появилось** ни в одном
признаке текущего дня, а есть только в целевом поле.

## 5. Тонкое место: курс ЦБ и выходные

Крипторынок торгует 365 дней в году. Банк России курс по выходным не
публикует.

**Решение:** берём последний известный курс и переносим вперёд, но **рядом
сохраняем его возраст** в поле `usd_rub_age_days`.

Реальное распределение на наших данных:
- возраст 0 дней — 2 147 суток (будни, курс того же дня);
- возраст 1–2 дня — около 900 суток (выходные);
- максимум 12 дней — новогодние праздники.

**Зачем возраст отдельным полем:** модель должна знать, что в понедельник
курс двухдневной давности. Иначе она считала бы пятничный курс таким же
свежим, как сегодняшний.

**Ещё одна оговорка:** USDT — не то же самое, что официальный доллар США.
Поэтому курс ЦБ используется как *возможный внешний признак*, а не для
пересчёта цены BTC в рубли. Полезен ли он — покажет эксперимент.

## 6. Почему выбраны именно эти показатели

**Объём (`vol`)** — поле завершённой свечи, в BTC. Оборот в USDT хранится
отдельно и объём не подменяет.

**Волатильность по Паркинсону:**
```
|ln(high / low)| / (2 · √(ln 2))
```
Считается по максимуму и минимуму **одних суток**.

**Почему не скользящее среднее за 10 дней:** соседние окна перекрывались бы
на 9 дней из 10, и соседние целевые значения оказались бы почти одинаковыми.
Модель показывала бы высокую точность просто потому, что ряд гладкий, — а не
потому, что что-то предсказывает.

## 7. Архитектура: почему три слоя, а не один

| Слой | Отвечает за | Можно ли перестроить |
|---|---|---|
| `raw` | Сохранить как пришло | Нет — это источник истины |
| `clean` | Проверить и типизировать | Да, целиком из `raw` |
| `mart` | Подготовить к анализу | Да, целиком из `clean` |

**Зачем разделять:** если показатель на дашборде выглядит странно, разделение
позволяет локализовать причину — плохие исходные данные, ошибка проверки или
ошибка расчёта признака. При одной таблице пришлось бы перезагружать всё
заново с биржи.

`raw` никогда не перестраивается — он неприкосновенен.

---

## 8. Контроль качества: почему строки не удаляются молча

Строка, не прошедшая проверку, **не попадает** в `clean`, но причина
записывается в `data_quality_log`: дата, вид проверки, подробности.

**Свойство, которое стоит назвать на защите:**
```
строк в raw = строк в clean + зафиксированных отбраковок
```

Это позволяет ответить на вопрос «а куда делись данные?». Если бы плохие
строки просто отбрасывались, расхождение в числах объяснить было бы нечем.

Семь проверок по типам из методички: полнота, допустимость, диапазон,
актуальность.

## 9. Найденная ошибка — хороший сюжет для защиты

Если спросят «с какими сложностями столкнулись» — вот честный ответ.

Тесты идут на SQLite в памяти (быстро, не нужна запущенная база). Первый
запуск в настоящей PostgreSQL упал:

```
psycopg.errors.InvalidSchemaName: schema "clean" does not exist
```

**Причина:** функция создавала только схему `raw`, а таблицы строились сразу
в трёх схемах. В SQLite схем нет — они эмулировались через `ATTACH`, и
ошибка не проявлялась.

**Исправление:** создавать все три схемы до создания таблиц.

**Вывод, который стоит озвучить:** тесты на SQLite проверяют логику, но
специфику СУБД можно проверить только на самой СУБД. Поэтому контрольный
прогон делается в PostgreSQL.

## 11. Демонстрация: что показывать

```bash
# 1. База поднимается
docker compose up -d db

# 2. Тесты — 23 passed
pytest

# 3. Повторная загрузка: rows_added = 0  ← идемпотентность
docker compose run --rm loader

# 4. Журнал загрузок
docker compose exec db psql -U pas_user -d pas \
  -c 'SELECT * FROM load_log ORDER BY id;'

# 5. Проверки качества
docker compose exec db psql -U pas_user -d pas \
  -c 'SELECT check_name, passed, count(*) FROM data_quality_log GROUP BY 1,2;'

# 6. Строка витрины с признаками и целью
docker compose exec db psql -U pas_user -d pas -x \
  -c 'SELECT * FROM mart.daily_market_mart ORDER BY candle_date DESC OFFSET 1 LIMIT 1;'
```

Пункт 3 — самый убедительный: нули в `rows_added` видно сразу.

## 12. Вопросы, к которым стоит быть готовым

**«Почему OKX, а не Московская биржа?»**
Сначала рассматривался фьючерс, но у него оказалось лишь 212 различных
торговых дней — мало для честной проверки модели по времени. У OKX
непрерывный суточный ряд с 2018 года, 3 174 дня.

**«Почему объём только одной биржи?»**
Так показатель измерим и проверяем по данным самой площадки. Это честнее,
чем заявлять оборот всего мирового рынка биткоина, который мы не можем
подтвердить.

**«Курс ЦБ точно помогает прогнозу?»**
Неизвестно. Он включён как *возможный* внешний признак; его полезность будет
проверена экспериментально при сравнении моделей. Заявлять пользу заранее
нельзя.

**«Почему тесты на SQLite, если база — PostgreSQL?»**
Тесты проверяют логику и проходят за 0.12 секунды без запуска базы.
Специфика СУБД проверяется отдельным прогоном в PostgreSQL — именно так и
была найдена ошибка со схемами.

**«Что будет, если биржа недоступна?»**
Временные ошибки повторяются автоматически до трёх раз. Если не помогло —
транзакция откатывается, в `load_log` появляется запись со статусом `failed`
и текстом ошибки. Данные не портятся, следующий запуск продолжит с той же
точки.

**«Система уже прогнозирует?»**
Нет. Готовы загрузка, очистка и витрина. Витрина построена так, чтобы
разделение на обучение и проверку выполнялось по времени. Точность пока не
измерена — заявлять её было бы неправдой.
